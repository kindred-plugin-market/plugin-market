# 2026-09-09

## 浏览器扩展导出能力调研

- 产出：`docs/browser-extension-export-research.md`（新建 `docs/` 目录）。
- 背景：用户希望 plugin-market 的能力（首个样本 photo-triage）能扩展为浏览器插件，Bench 侧提供「导出为浏览器扩展」按钮。
- 核心结论：
  1. 静默自动安装**不可行**（Chrome/Edge/Firefox/Safari 均禁止第三方静默安装）；最接近的是「打开 chrome://extensions + 引导式加载已解压目录」（P0），真正的一键需上架 Chrome Web Store 后用内联安装（P1）。
  2. 推荐架构：**Native Messaging 为主 + File System Access 为降级**的双模 Runtime Adapter；大图字节流走本地 HTTP 旁路。
  3. photo-triage 的 15 个命令中，`trash / restore / original_path / reveal` 在纯浏览器环境无解（无系统废纸篓、FSA 屏蔽真实路径）。
  4. 代码可复用率估 70–85%（UI/算法/控制器可复用，`src/services/*` 需重写为 adapter）。
  5. 构建工具推荐 WXT（跨浏览器最好、Vite 底座），产出一份代码多浏览器构建。
  6. CWS：Single Purpose Policy → 必须一个插件一个扩展 ID；`nativeMessaging` 是敏感权限必触发人工审核；$5 一次性 + 2FA。
- 用户尚未确认要进入实现阶段，下一步取决于是否批准 Spike（6 项待验证，重点：扩展页内 showDirectoryPicker 可用性、Native Messaging 1MB 上限实测）。

## 能力外溢方向规划（浏览器扩展之外）

- 产出：`docs/extension-targets-roadmap.md`。
- 核心框架：插件 = View（React，平台无关）+ Capability（Tauri IPC，平台绑定）；外溢方向按三类归位——A 换宿主（浏览器/VS Code/Raycast/Obsidian）、B 换形态（CLI/MCP/npm SDK/Web）、C 换触达（菜单栏/Finder/Quick Look/快捷指令）。
- 最重要洞察：**MCP 的 stdio transport 与 Chrome Native Messaging 是同一形态**（父进程起子进程 + stdin/stdout + JSON + 能力清单）。建了 Native Messaging Host 后，包一层 MCP JSON-RPC 语义即得到 MCP Server —— 一次投入两个宿主。
- 优先级判断：T0 = MCP Server（边际 2–4 pd）+ Web/PWA（hardware 是纯前端零 IPC，静态部署近乎零成本）；T1 = CLI（被低估的底座，有它后 MCP/自动化/Raycast Script Command 成本都降）+ 浏览器扩展 + VS Code（terminology 场景最契合）；T2 = Raycast（React+TS 技术栈完全同构、免费、审核 3–7 天）+ 菜单栏 App；T3 = Obsidian/uTools/原生系统扩展。
- 时效性：VS Code 市场发布所用的 Azure DevOps 全局 PAT **2026-12-01 退役**，须迁移到 Entra ID workload identity federation。
- 另提出「市场平台化」方向（第三方开发者生态、插件签名、权限审计面板），并给出判断：若 Bench 定位是平台，第三方生态应优先于第 3、4 个宿主。
- 留了 3 个待用户决策的问题：Bench 是工具还是平台 / Windows 排期 / 是否接受降级带来的语义不一致成本。

## 定案：MCP + 浏览器扩展 为后续开发方向（实施手册）

- 用户拍板：浏览器插件与 MCP 共同列为后续开发方向，要求调研具体操作并沉淀 md。
- 产出：`docs/implementation-playbook-mcp-and-browser.md`（实施手册，非可行性分析）。
- **技术选型关键发现（改变了架构）**：MCP 官方 Rust SDK `rmcp` 于 2026-08-21 从 Tier 2 晋升 **Tier 1**（与 TS/Python/C#/Go 同级，一致性 server 67/67、client 50/50），当前 v3.1.2，实现 MCP 2026-07-28 规范。因 Bench 本体是 Rust/Tauri，**无需引入 Node 运行时**。
- **定案架构**：抽 `bench-capabilities` crate（纯业务逻辑，无协议无 GUI，Bench app 与 host 共用，零重复）→ `bench-host` 单 Rust 二进制按 argv 切四种角色：`--mode mcp`（rmcp stdio）/ `--mode native`（Native Messaging 4 字节前缀帧）/ `--mode serve`（本地 HTTP 图片旁路）/ `--mode cli`。该二进制同时作为 Tauri v2 sidecar（`bundle.externalBin`）打包。
- **MCP 应排在浏览器扩展之前的决定性理由**：MCP「安装」= 写一个 JSON 配置文件，Bench 可完全自动化（探测客户端 → 深合并写 mcpServers.bench → 备份 → 校验回滚 → 提示重启）；而浏览器扩展必须用户手动开开发者模式，无法自动化。
- 安全决策：**不暴露任何删除类 MCP tool**（2026 年初两个月 30+ MCP CVE，仅 12.9% 服务器高信任）；删除留在 Bench GUI 内。若需，只提供 `*_preview`。
- 关键工程坑：MCP 与 NM 共用 stdout → 日志必须全走 stderr，CI 需加 stdout 纯净性冒烟断言；WXT 要求浏览器 API 调用必须写在 `main()` 内；扩展必须固定 `key` 锁定 ID 否则 NM 的 allowed_origins 失效；Native Messaging 不带参数故需 wrapper 脚本。
- 工作量：M0 能力内核 3–5 pd / M1 host 骨架 2–3 pd / M2 MCP 3–4 pd / M3 浏览器扩展 8–12 pd / M4 打包分发 2–3 pd，合计约 18–27 pd。
- 未决：Q1 现有 Rust 代码耦合度未知，建议开工前花 0.5 pd 勘察再校准估算。
